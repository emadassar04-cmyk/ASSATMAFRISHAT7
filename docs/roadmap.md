## المرحلة 1 — الواجهة العامة + الأقسام والمنتجات + لوحة المشرف ✅ (مكتملة بموافقة صاحب المشروع)
**النطاق**
- مشروع Next.js (App Router, Tailwind, RTL) + Design Tokens + PWA + إعدادات من DB.
- Migrations: الهوية، الإعدادات، الفروع، الكتالوج، العروض، التخزين + RLS + Seed.
- تسجيل الدخول بالجوال (OTP عبر واتساب/تلجرام)، وتسجيل دخول الموظفين مع بنية الأدوار.
- الصفحات: الرئيسية، الأقسام والمنتجات (فلترة/بحث)، صفحة المنتج (بدون إتمام طلب)، العروض، الفروع، من نحن/تواصل، السياسات، الخصوصية/الشروط/حذف البيانات، Meta Tags وSitemap وOG.
- لوحة المشرف: أقسام (سحب وترتيب وأقسام فرعية)، منتجات وخصائص وVariants وصور وأسعار ومخزون لكل فرع، عروض، استيراد/تصدير CSV/Excel.
- مسار رفع الصور الموحّد (جاهز لتمديد WebP).
- لوحة الإدارة: الإعدادات الأساسية (المتجر، الثيم، الفروع/الدوام، السياسات) + إدارة المستخدمين والأدوار.
- إعداد Vercel (مشروع، Preview/Production)، Supabase للتطوير/الإنتاج.

**Acceptance Criteria**
- [x] لا يوجد اسم متجر/فرع/قسم/لون/سياسة مكتوب في الكود (فحص آلي grep + مراجعة)؛ تغيير الاسم والألوان من الإعدادات ينعكس على الموقع.
- [x] RTL كامل؛ لا ملف يستخدم `ml-/mr-/left/right` فيزيائياً دون سبب (lint rule).
- [x] إضافة فرع جديد وقسم جديد وخاصية جديدة من اللوحة دون تعديل كود. (تأكيد صاحب المشروع)
- [x] RLS: اختبارات pgTAP تمر لكل دور على كل جدول مرحلة 1؛ الزائر لا يرى المخفي؛ المشرف لا يصل للإعدادات.
- [x] Lighthouse على جوال (محاكاة 3G بطيئة): Performance ≥ 85، LCP ≤ 3.5s على الرئيسية وصفحة المنتج؛ وزن الصفحة الأولى ≤ 300KB JS مضغوط.
- [x] الصور Lazy + نسبة موحدة؛ PWA قابل للتثبيت ويعمل offline للصفحات الأساسية (shell + آخر قائمة مخزّنة).
- [x] استيراد CSV ينشئ/يحدّث منتجات مع تقرير أخطاء صفّي، والتصدير يعيد نفس البيانات (Round-trip). (تأكيد صاحب المشروع + اختبارات matchVariant)
- [x] ~~OTP بالجوال~~ ← استُبدل بقرار صاحب المشروع بتسجيل الدخول عبر Google (Gmail) مع 2FA للإداري؛ الدخول يعمل على الإنتاج.
- [x] 2FA (TOTP) مفروض لحسابات Admin.
- [x] اختبارات: Unit للمنطق، E2E (Playwright) لتصفح الكتالوج والبحث والفلترة وإدارة منتج.
- [ ] OG يظهر صحيحاً (صورة/اسم/سعر) في معاينات الروابط. — وسوم OG (الاسم والسعر) متحقَّق منها في الـHTML؛ معاينة روابط فعلية على فيسبوك/واتساب لم تُفحص بعد (لا صور منتجات بعد).

## المرحلة 2 — الطلبات والدفع + لوحة الزبون + لوحة الإدارة + التدقيق — **مكتملة جزئياً بقرار صاحب المشروع (تأجيل إشعارات n8n/تلجرام)**؛ التقرير: `docs/phase2-report.md`
**النطاق**
- Migrations: الطلبات، الدفع، الطلبات المفصّلة، Outbox، Audit Log + triggers + immutability.
- السلة (محلية) وإتمام الطلب: الفرع، الدفع، رفع الإيصال (Bucket خاص)، Checkbox سياسة الاستبدال.
- `create_order` RPC + Outbox + Retry (Cron) + ربط n8n الأساسي: WF-03 وWF-07 وWF-10 وWF-11 وWF-13 (بحد أدنى).
- نموذج طلب التفصيل + العربون (من الإعدادات).
- لوحة الزبون: طلباتي، حالة، رفع إيصال، طلبات التفصيل، المفضلة، بياناتي.
- لوحة الإدارة: الطلبات، تأكيد/رفض الدفعات، الإحصائيات المبدئية للطلبات.
- Audit Log كامل + لوحة مشرف المتابعة (Auditor) + تنبيه تلجرام للتعديلات الحساسة.

**Acceptance Criteria**
- [x] لا يمكن إنشاء طلب بدون موافقة سياسة الاستبدال (اختبار على الواجهة والـ RPC). — مُختبر في RPC (118 فحصاً) والواجهة تفرض الـ checkbox والخادم يتحقق.
- [x] لا يمكن للعميل التلاعب بالسعر؛ الاختبار يرسل سعراً مزوّراً فيُتجاهل. — حمولة الواجهة بلا أسعار، والقاعدة تتجاهل أي سعر/إجمالي/حالة يُرسل.
- [ ] رفع إيصال: فقط jpg/png/webp/pdf ≤ 5MB؛ مخالف يُرفض؛ الزبون لا يقرأ الإيصال، الإداري يقرؤه عبر رابط موقّع قصير. — **جزئي**: حدود bucket (5MB، jpg/png/webp/pdf)، ومسار الطلب، وقراءة الإداري بروابط موقّتة (دقيقتان) منجزة ومُختبرة؛ **واجهة رفع الإيصال للزبون لم تُبنَ** لأن الدفع بالاتفاق عبر واتساب/فيسبوك (الدالة `submit_payment` جاهزة).
- [ ] **لا يضيع طلب**: إيقاف n8n، إنشاء 10 طلبات، تشغيله ← تصل كلها مرة واحدة (Idempotency) في الترتيب. — **مؤجَّل**: جدول Outbox بمفاتيح idempotency يُكتب مع كل حدث في نفس معاملة الطلب؛ ينقص مُرسِل Cron وربط n8n.
- [ ] تأكيد الدفعة يغيّر الحالة، ويكتب Audit، ويصل إشعار للزبون على قناة المصدر. — **جزئي**: تغيير الحالة والتدقيق منجزان ومُختبران؛ إشعار الزبون على قناة المصدر مؤجَّل (n8n).
- [x] Audit Log: أي UPDATE/DELETE عليه (حتى بـ service_role) يفشل؛ كل تعديل على المنتجات/الأسعار/الطلبات/الدفعات/الإعدادات/المستخدمين يظهر بالقيمتين القديمة والجديدة والفرع. — التعديل مرفوض حتى لـ postgres و service_role، والحذف/التفريغ بـ triggers، والقيم القديمة/الجديدة والفرع مسجّلة.
- [x] الـ Auditor: يقرأ ويفلتر (مستخدم/نوع/تاريخ/فرع) ولا يستطيع أي كتابة؛ 2FA مفروض. — (صفحة `/dashboard/audit` + تصدير CSV؛ لم تُفحص بجلسة مدقق حقيقية بعد).
- [ ] تغيير سعر/حذف منتج/إلغاء طلب/تأكيد دفعة ← تنبيه تلجرام خلال < 30 ثانية. — **مؤجَّل**: الأحداث الحساسة تُكتب في Outbox (مُختبر)؛ التنبيه نفسه ينتظر تلجرام/n8n.
- [x] Moderator لا يرى الطلبات ولا الإحصائيات المالية ولا الإعدادات ولا السجل (اختبارات RLS).
- [ ] Webhooks الموقع↔n8n تُرفض بدون توقيع صالح أو بتوقيت قديم. — **مؤجَّل** (n8n).
- [ ] اختبارات: RLS pgTAP كاملة، Unit، E2E لمسار الطلب الكامل والدفع والرفض. — **جزئي**: RLS pgTAP كاملة (118 + 19 + 43 + 13 + 7)، وحدة 54، E2E 40؛ E2E لمسار الطلب الكامل بجلسة مسجّلة غير مؤتمت.

## المرحلة 3 — الشات بوت + القنوات + النشر + الإحصائيات
**النطاق**
- Migrations: المحادثات، الرسائل، KB + pgvector، المنشورات.
- AI Agent (WF-02) + الأدوات (`bot_*`) + RAG + نصوص البوت من الإعدادات.
- ماسنجر (WF-01a) + تعليقات فيسبوك وPrivate Reply (WF-05) + واتساب (WF-01b + القوالب) + تلجرام (WF-01c) + شات الموقع (WF-01d).
- Human Handoff + Unified Inbox + «إعادة للبوت» + خارج الدوام وملخص الصباح (WF-04, WF-09, WF-06).
- النشر بالموافقة (WF-08) + مزامنة كتالوج فيسبوك (WF-12) + Meta Pixel.
- الإحصائيات الكاملة في لوحة الإدارة.
- هوية الزبون الموحدة عبر القنوات.
- تصدير كل Workflows إلى `/n8n`.

**Acceptance Criteria**
- [ ] اختبارات السلوك الثمانية في `docs/ai-agent-prompt.md` تمر (مع سجل نتائج).
- [ ] صفر اختراع: 50 سؤالاً عن أسعار/توفر ← كل إجابة مطابقة لـ DB (فحص آلي)؛ سؤال بلا جواب ← عرض تحويل.
- [ ] نفس الزبون من واتساب وتلجرام (بنفس الرقم) يظهر بسجل موحّد للموظف والبوت.
- [ ] Handoff: يتوقف البوت فوراً؛ إشعار للمجموعة؛ رد الموظف يصل لنفس القناة؛ زر الإعادة يعيد البوت.
- [ ] خارج الدوام: النص الحرفي المعتمد، المحادثة `waiting`، وملخص مرتب من الأقدم عند بداية الدوام.
- [ ] واتساب: داخل 24 ساعة نص عادي، وبعدها Template معتمد؛ ولا إرسال بقالب غير معتمد.
- [ ] توقيعات Meta/Telegram مفروضة (طلب بتوقيع خاطئ يُرفض 401/403).
- [ ] تعليق «السعر؟» ← رد عام + رسالة خاصة خلال < 30 ثانية.
- [ ] نشر: توليد نص ← تلجرام بأزرار ← تعديل ← إعادة عرض ← موافقة ← نشر ← حفظ الرابط؛ الرفض لا ينشر.
- [ ] الإحصائيات تطابق بيانات DB (طلبات/فرع/فترة، الأكثر طلباً ومشاهدة، المبيعات بالدفع، المصدر، نسبة البوت للموظف، متوسط وقت الرد، المنتجات النافذة).
- [ ] Rate Limiting على الشات والنماذج (اختبار تجاوز الحد).
- [ ] صفحات Meta (الخصوصية، الشروط، حذف البيانات) منشورة وتعمل في إعداد التطبيق.
- [ ] كل Workflow مصدَّر ومحدَّث في `/n8n` وخالٍ من الأسرار.

**Acceptance Criteria**
- [ ] تغيير التصميم بالكامل بتعديل Tokens ومكوّنات محدودة دون لمس منطق الأعمال.
- [ ] كل صورة جديدة تُخزَّن WebP مضغوطة بمقاسات متعددة مع لوجو؛ الصور القديمة تُعالج بـ Migration/Job.
- [ ] التوصيل: تفعيل من الإعدادات، منطقة وسعر عند الإتمام، دون تغيير مخطط الجداول الأساسية.
- [ ] لا تراجع في الأداء (Lighthouse لا يقل عن المرحلة 1).
